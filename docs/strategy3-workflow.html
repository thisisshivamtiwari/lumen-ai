Phase A · establish trustworthy inputs
01

Confirm the task and observation rules

Decide what the model must predict and what it may see.

We score transactions, even though laundering evidence may span many payments. Start by recording the exact target, positive-label meaning, eligible IDs, score format and allowed data sources. The supplied release instructions take precedence if they update the training deck.

  1. Read the README, scorer, baseline and submission example. Confirm TRANSACTION_HASH,score, expected test IDs and score range.
  2. Check whether train/test represent separate worlds or successive windows, whether wallets overlap, and whether scenarios or difficulty tags are supplied.
  3. Confirm retrospective whole-week context versus historical-only features. Separately confirm whether train and test unlabelled graphs may be combined.
  4. Record external-data and preparation rules, AI disclosure requirements and approved licence requirements.
Default while unresolved: causal features

Use only earlier supported activity and record the limitation. A static AP leaderboard does not itself authorise future context. This selector illustrates the plan; it does not grant permission or run a pipeline.

Pass when

We have a written contract and an explicit context mode. If a detail remains unclear, use a documented conservative fallback and keep it visible in the decision log.

Output: proposed contract.md containing targets, rules, visibility and unresolved questions.

02

Audit every raw file and build the ID spine

Protect row identity before doing any modelling.

Create a fixed table of all required transaction hashes, with a split indicator and original order. All later features join back to this spine. A transaction with incomplete flow evidence still receives a prediction if it is eligible under the contract.

What we measure

  • Row counts, data types, nulls and duplicate keys in every file.
  • Training class prevalence and the number of positive-bearing groups, if groups exist.
  • Timestamp coverage, ledger range, orphan transfer/label rows and missing rates.
  • Train/test wallet, pair, asset and exact-record overlap; investigate overlap without assuming it is forbidden.

What we assert

  • Transaction hashes identify the expected target rows uniquely.
  • Labels map to the correct training transaction; missing labels are not assumed negative.
  • Ledger and rate joins have documented cardinality.
  • Joining features never drops or duplicates target transactions.
Why this comes first

A conversion with three transfer rows can multiply one labelled transaction into three training rows during a naive merge. The model may look successful while its training target and eventual submission are wrong.

Pass when

Counts reconcile with the released contract, exceptions are explained, and every required transaction has exactly one target-spine row.

Output: data audit, immutable target ID tables and explicit join checks.

03

Reconstruct economic payments correctly

Separate who paid whom from how the ledger executed the payment.

Inspect payments.py first, then reconcile its output with raw examples. Maintain an economic payment graph and a separate execution-leg table. The first is for actor behaviour; the second explains conversions and reconstruction quality.

Economic view

Sender → ultimate receiver

One payment event with transaction ID, time, paid/delivered asset and value, status and quality flags. Preserve repeated payments between the same pair.

Execution view

Sender → LP → receiver

Retain liquidity-provider legs, path structure and asset changes. These are atomic parts of one transaction, not independent laundering hops.

  1. Parse documented JSON representations. Preserve malformed/missing states separately from valid zero.
  2. Keep XRP in exact integer drops for reconciliation; 1 XRP = 1,000,000 drops. Keep token currency and issuer identity together.
  3. Use delivered value for receipt and actual paid value for expenditure; SendMax is a ceiling. Check partial-payment semantics only where relevant.
  4. Join the documented asset key to the containing UTC rate hour. Retain native values plus USD values and missing-rate indicators.
  5. Use documented ledger/transaction ordering where available. Equal timestamps alone do not prove event order.
  6. Keep failed/no-transfer target rows, but do not invent completed-flow edges. Preserve self-conversions as a distinct case rather than automatic cycles.

Pass when

Hand-reconciled plain payments, conversions and missing-data cases match the pipeline. Economic totals count each payment once and every required target remains present.

Output: canonical payment table, execution-leg table and reconstruction audit.

04

Prepare isolated synthetic scenario fixtures

A development branch that can begin before real data arrives.

Generate small examples with known structure to verify our parser and graph features. Start with economic edges; add execution legs for conversion cases. These examples test correctness, not expected leaderboard AP. A full 40k-scale development dataset is optional after the small fixtures pass.

Scenario familyFixture to constructLegitimate comparison
Fan-in / fan-outSeveral sources collect into a hub; one source splits to several recipients.Merchant collections, recurring payroll and withdrawals.
Scatter-gather / gather-scatterMultiple two-hop routes; or many-in/many-out through a hub.Treasury rebalancing and payment processors.
Cycle / layered stackClosed paths and multi-layer intermediary chains.Refunds, tiny bot loops and processing chains.
Bipartite / irregular networkDense directed group-to-group flows; branching and overlapping paths.Marketplace and ordinary peer activity.

Vary duration, amounts, counterparties and conversion frequency on both sides. Include partial forwarding, overlapping scenarios, repeated transactions, equal timestamps, interrupted boundary flows and benign payments by scenario participants.

Keep scenario truth separate

Store labels, scenario IDs, motif roles, expected paths and generator settings outside feature inputs. Do not encode the class in addresses, hash formats, row order or missingness. Seeds and assumptions must be recorded. Ambiguous examples can be diagnostic-only rather than forced ground truth.

What synthetic tests should actually prove
  • A three-leg conversion produces one economic payment, not a three-hop cycle.
  • Repeated payments remain separate events and one prediction row is preserved per hash.
  • A structural cycle without valid time ordering differs from a chronological cycle.
  • A rate join never multiplies rows; malformed fields remain flagged rather than silently zeroed.
  • We know exactly which test edges should participate in each motif. This verifies features, not the validity of an intent classifier.
Pass when

Known-answer structural and numerical checks pass. Keep generated data isolated from competition training unless the organisers explicitly permit that use.

Output: proposed fixture inputs, separate truth table and a short correctness report. No fixtures have been generated by this HTML guide.

Phase B · establish measurable learning
05

Choose validation before experimenting

Make our local score answer the intended generalisation question.

A random row split can share wallets and pieces of one laundering scenario across training and validation. Conversely, grouping every connected wallet can put most data into a single exchange-linked component. Inspect the released data before choosing a split.

  1. Prefer genuine scenario groups if supplied and appropriate. Keep related labelled events together and check enough positives remain in each fold.
  2. If groups are absent, inspect component sizes, wallet/pair overlap and time structure. Document a primary holdout justified by those observations; pseudo-groups are imperfect.
  3. Add a small entity/pair-disjoint stress check and a chronological/boundary check where feasible. They diagnose different failure modes, not interchangeable scores.
  4. Match allowed context: causal features see only earlier events; permitted batch features may use unlabelled whole-window context. Do not automatically combine train/test graphs.
  5. Fit imputation, encoders and other learned transformations inside training folds. Keep held-out labels out of feature building and every model stage.
Topology versus labels

In an explicitly authorised retrospective setting, unlabelled validation edges may be visible as graph context. Their labels remain hidden. A stress test that removes those edges answers a different question; label the two evaluations clearly.

Pass when

Split IDs, seeds, class counts, permitted context and fitting rules are saved. Keep a confirmation holdout untouched if the number of independent positive groups allows it.

Output: frozen split assignments and a small validation matrix used by every candidate.

06

Run a simple baseline and verify exact AP

Obtain a valid end-to-end result before sophisticated features.

Run the supplied baseline, then a compact CatBoost or LightGBM model using available packages. Start with basic payment values, conversion/status fields, safe transformations and data-quality masks. Use hashes for alignment, not arbitrary ID ordering as a shortcut predictor.

Training objective

A standard binary loss is a reasonable starting point. Keep the configuration modest and reproducible. Choose the best model and stopping point using the exact held-out AP definition.

Selection objective

Rank positives ahead of negatives. Do not tune a 0.5 threshold. Scores must satisfy [0,1] for submission, but probability calibration is not required by the ranking objective.

AP intuition

If two suspicious transactions occur at ranks 1 and 3, their precisions are 1/1 and 2/3. With distinct scores, AP = (1 + 2/3) / 2 ≈ 0.833, so the score is about 83.3. Equal scores are grouped; verify tie behaviour with the official scorer.

  • Use exact Average Precision, not an assumed equivalent trapezoidal PR-AUC.
  • Record fold AP and pooled out-of-fold AP separately; they can differ because fold score scales differ.
  • Keep output precision. Rounding, isotonic calibration and rank blending can introduce ties or change useful ordering.
  • Produce and validate a baseline-format CSV early so a working fallback exists.
Pass when

The baseline runs from raw inputs to a complete, valid score file. Its predictions, AP, configuration and runtime are saved; no performance target is invented before measurement.

Output: baseline model, prediction table, metrics and known-good submission-format file.

Add transaction and wallet behaviour

Describe direction, recurrence, timing and scale before searching complex motifs.

Begin with a few short, medium and long windows—for example 5 minutes, 1 hour and 24 hours, plus permitted observed-window summaries. These are starting experiments, not known optimal settings. Add 1-minute, 6-hour or 72-hour windows only for a clear missed case.

Keep both raw and locally normalised quantities. Exclude the current event from reference statistics where the feature definition calls for other activity. Record whether counts are before-only, after-only or whole-context so training and inference use identical meanings.

Pass when

Each feature block is added separately, has sensible distributions, uses permitted context and improves the fixed validation comparison without an unexplained serious regression.

Output: a versioned feature dictionary and an experiment log with baseline-versus-candidate AP.

08

Add bounded graph and money-flow features

Describe this payment’s role in a structure, not just its proximity to a busy wallet.

PatternTransaction-level evidenceImportant counterexample
Fan-in / fan-outDistinct participants, event density, amount dispersion, edge’s source/sink role.Merchant collections and payroll.
Scatter-gatherSeveral bounded paths sharing economic source and destination; combined-value compatibility.Corporate treasury rebalancing.
Gather-scatterMany-in/many-out, lag distributions, local retention proxy and outside connectivity.Exchange and processor activity.
CyclesBounded return paths, edge participation, elapsed time and returned-value compatibility.Refunds, arbitrage and bots.
Layered stackBounded depth, intermediary activity, flow compatibility and delays.Legitimate processing chains.
Bipartite / irregularLocal directed density, branching, converging paths and temporal concentration.Marketplaces and ordinary connected communities.
  1. Preserve a directed multigraph: parallel payments are separate events. Start with bounded 2–4-hop searches and capped work at hubs.
  2. Compute static participation and time-respecting participation separately. Chronological paths need distinct economic transactions with supported order.
  3. Compute short hold times and graded value-compatibility features. Support splits, merges and partial forwarding rather than strict one-to-one equality.
  4. For same-asset flows use native-value comparisons; for cross-asset paths use USD compatibility with uncertainty for spread, rates and fees.
  5. Emit cap/truncation and ambiguity indicators. Do not mistake an interrupted search for absence of a pattern.
A possible route is not proven fund provenance

We lack complete starting balances and intent. Compatible deposits and exits support a feature; they do not prove which deposit financed which exit. Avoid hardcoded FIFO assignment, fixed fee tolerances and component-wide suspicious labels.

Pass when

Fixtures confirm motif definitions, high-degree cases stay within budget, and paired real-data validation shows useful gains over behavioural features alone.

Output: role-specific motif features, runtime/cap diagnostics and a graph-feature ablation.

Phase C · challenge the model and ship
09

Inspect mistakes and challenge our assumptions

Use predictions and transaction traces to decide what to improve next.

Inspect high-ranked legitimate transactions and low-ranked suspicious transactions from held-out data. Trace the economic payments and execution details for representative mistakes. Keep every proposed change tied to a specific observed failure.

False-positive review

Exchange hubs, payroll, merchants, treasury, refunds, dust loops and self-conversions. Check whether degree, amount or asset rarity overwhelms context.

False-negative review

Slower chains, incomplete cycles, partial forwarding, overlapping scenarios, suspicious edges in otherwise legitimate accounts and sparse-context events.

  • Compare known/unseen endpoints, recurrent/new pairs, conversions, amount tails and missing-data cohorts.
  • Check first/last-day sensitivity. “First observed” is not account creation; observed net flow is not account balance.
  • If tags exist, scope them to their address. Equal tag numbers across addresses do not establish the same person.
  • Report positive/negative counts with slice AP. Compare candidates on the same rows; AP across different-prevalence slices is not directly comparable.
  • Difficulty-only positive subsets cannot provide useful standalone AP. Use a fixed justified negative background and global top-ranked recall diagnostics.
How we keep or reject an experiment

Save the hypothesis, changed feature block, exact split IDs, paired prediction files, AP, slice regressions and runtime. Keep the change only when it improves the primary comparison and has no material unexplained robustness or runtime failure. Investigate gains concentrated in one scenario; do not keep searching until one split happens to look good.

Pass when

We can explain the dominant errors and the selected model’s limitations. Optional complexity has evidence behind it, and the fallback remains available.

Output: error examples, slice report and an accepted/rejected experiment log.

10

Try optional improvements only if time permits

The first reliable ranker remains the default.

Conditional

Shift diagnosis

Train a train-versus-test classifier if allowed. Inspect separating features and perform supervised ablations. A calendar or asset difference is not automatically leakage or a reason to delete a useful feature.

Conditional

Complementary model

Try a second tree family or feature view. Compare its errors and AP with the best model. Different seeds alone do not prove useful diversity.

Conditional

Ensemble

Compare probability mean and normalised rank mean against the strongest member on identical holdouts. Keep only a measured benefit; rank means can create ties.

Advanced neighbour-risk stage: why ordinary OOF is insufficient

Edge A’s own out-of-fold score may exclude A’s label. But neighbour B’s OOF model may have trained on A. Adding B’s score back to A can indirectly leak A’s target.

  1. Hold an outer validation group completely out of all first-stage fits.
  2. Inside outer training, create inner-cross-fitted predictions for stage-two training features.
  3. Generate validation and permitted context scores using outer-training models only.
  4. Exclude self/duplicate contributions, then assess the complete stage-two pipeline on untouched outer labels.
  5. Check that inner-fold training scores and final inference scores are sufficiently aligned.

If this construction cannot be implemented and audited before freeze, skip stage two. Do not substitute component-max smoothing or in-sample neighbour probabilities.

Pass when

The optional addition beats the best simpler model honestly, remains reproducible and fits the remaining time. Otherwise retain the simpler model. Broad GNN adoption and heavy dependency changes remain deferred.

Output: documented final candidate choice; optional does not mean required for completion.

11

Freeze the method and generate test predictions

Turn the chosen experiment into a deterministic inference path.

  1. Select feature blocks and hyperparameters using validation. Run the untouched confirmation check if one was reserved.
  2. Save seeds, configuration, split IDs, feature definitions, dependency versions, source version and permitted context mode.
  3. Fit the selected pipeline on all allowed labelled training data. Refit learned transforms consistently; keep test labels unavailable.
  4. Build test features with the same code and agreed context. Do not switch from causal training features to future-aware inference or silently combine graphs.
  5. Predict continuous scores, join back to the test spine and preserve full output precision.
  6. Validate exact membership in the released test ID set, not just a total row count. Preserve required order if the release specifies one.
Completion is a contract, not a promised score

We need 40,101 unique expected test hashes under the deck’s specification, each with one finite score in [0,1]. No missing, extra or duplicated IDs; no manual test labels. If the release changes the count, the verified contract controls.

Pass when

The final score file passes identity, numeric, schema and size checks, and we can reproduce it from documented inputs and settings.

Output: proposed predictions.csv, model/configuration and final local verification record.
