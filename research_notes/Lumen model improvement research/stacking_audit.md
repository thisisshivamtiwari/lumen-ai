# Validation and provenance audit of the Lumen V3/V4 context stack

## Are labels excluded from every level of context stacking?

### Takeaway
The observed construction excludes the **outer held-out fold's labels** from all first-stage scores and the second-stage fit. That is meaningful protection: the measured V4 gain cannot simply be dismissed as held-out-label leakage. However, the stronger claim that a meta-training row's entire context is target-excluded is false: its label can influence the scores of neighbours, which then enter that row's context. This is a training feedback path and a possible train/inference mismatch, whose effect is not established by inspection alone.

Its official documentation also warns against training a stack on predictions fitted on the same target rows. The latter graph-specific conclusion is this audit's inference, not an assertion made by the documentation. ### Inferences
- **Minimal target-excluded construction:** keep outer test fold F fixed and let T be all permitted fit labels. Make grouped inner blocks B within T. For each B, fit a base model on T\B; use that **one model's score bank for the entire observable window**, then extract context only for centres in B. No input score for those centres can depend on y_B. Assemble these centre-wise contexts to fit stage 2 on T. Fit a base model on all T, score the entire observable window, construct context for centres in F, and evaluate stage 2 on F. Ranking, tie-breaking, feature options and model selection must be fixed inside this wrapper.
- **Matching final inference recipe:** repeat the same inner grouped construction on all labelled training data to obtain target-excluded centre-wise training context; fit stage 2 on that context. Fit stage 1 on all training labels; score the complete test window and build test context from that score bank; apply stage 2 and the exact frozen blend function. This is a concrete correction for the indirect own-target dependency. It is **not** a claim that training and test distributions become identical.
- A remaining issue in that minimal recipe is that some training-window neighbours have in-sample predictions from the centre-excluding model, whereas every test-window payment is unseen by the model. A stricter optional diagnostic uses a bank excluding both the centre block B and the neighbour block C, requiring at least three inner blocks and explicit handling of B=C. A matched honest sample-split or disjoint-window experiment is another diagnostic. Neither should be silently mixed with the current 3-fold recipe; it changes the learning problem and needs its own outer evaluation.
- Ranks only align marginal order/scale. They cannot erase which labels trained a source model, correct wrong score ordering, or guarantee comparable neighbour dependence. Current outer training scores use models trained on 13,377 rows versus 26,754 for outer targets; final training OOF sources use 26,754 versus 40,131 for test. This smaller-fit/full-fit difference is common in stacking, but the graph aggregation makes checking it particularly relevant. [Row counts in the existing fixed-fold evidence](/Applications/Softwares/Lumen.ai/outputs/v2_experiments/baseline_recomputed_metrics.json), [packaged run_v3.py:59](/Applications/Softwares/Lumen.ai/outputs/v4_motif_context/lumen_v4_code/run_v3.py:59)
- **Mandatory before making a stronger no-leakage claim:** generate a provenance matrix `(centre block, neighbour block, source model, source fit blocks)` and assert the centre and outer heldout labels are excluded; test with cached/toy score banks and label-dependency sentinels. A real label-permutation refit is stronger but is not lightweight and was not performed here. Passing ordinary `score(j)` OOF checks alone is insufficient.

### Gaps
- No saved single-fold score banks or per-bank fit-membership manifests were present in the inspected V3 output inventory, so the source assignment was verified from code, not a replay of each fitted model. No magnitude for the indirect feedback effect is claimed.
- The minimal corrected recipe above has not been fitted or compared with V4. Its effect on AP could be positive or negative; preserving honest outer evaluation matters more than assuming that removing feedback must improve the leaderboard.

## Are score comparison, uncertainty and artifact provenance measuring the same candidate?

### Takeaway
The V4 OOF blend is reproducible from saved stage scores, and its original-fold improvement is substantial. However, pooled ranking normalization, the bootstrap comparator and packaged experiment paths need tighter labels. Active source/cache drift is real and expected during development; it is a release-management risk, not proof that the already frozen V4 ZIP or its predictions are wrong.

### Inferences
- Claim the original-fold result as **61.616 mean fold AP**, with **61.527 pooled per-fold-normalized OOF AP** explicitly labelled. Preserve frozen **raw** V1 as the promotion comparator. Report per-fold top-1% performance as well as the global 402 diagnostic; neither should silently replace the other.
- Recalculate a candidate-named, hash-bound conditional group bootstrap for the latest frozen candidate versus raw V1; report point estimates for AP and top-1% catches and separately say it does not correct selection/retraining uncertainty. The earlier context interval does not certify V4.
- A reported +6.4 leaderboard movement is encouraging but does not certify every new feature, holdout or future version; adding a constant portal/local offset to forecast the next score is unsupported. Do not claim “validation is trustworthy” without retaining its explicit scope and uncertainty.
- A five-seed V1 control is evidence against seed averaging alone explaining the earlier result. It is not a seed confirmation of the motif/context candidate, and does not isolate all effects of architecture, normalization and blending. One longer-training setting failing likewise does not prove the model is not capacity-limited.

## What should be checked next without duplicating ongoing experiments?

### Takeaway
The next work should make the existing improvement auditable before adding another complex model. The five priorities below preserve every original promotion gate and can begin with saved scores, provenance assertions and package checks; fitting is deferred to the main working agent's authorized schedule.

### Cited Findings
- Original gates require at least **0.01 absolute mean-fold AP improvement**, improvement on at least **two of three folds**, a positive paired-group CI lower bound, a positive confirmation-seed improvement, and no more than **0.02 AP regression** on wallet/temporal diagnostics. The subsequent Run 1 investigation also requires **no global top-1% TP loss** and source reproduction. The thresholds are local governance choices, not statistical guarantees. [audit.py:26](/Applications/Softwares/Lumen.ai/outputs/v2_experiments/source_v2/audit.py:26), [Run 1 acceptance checks](/Applications/Softwares/Lumen.ai/outputs/run1_investigation/acceptance.json)
- Nested validation must include feature/blend selection if its score is to estimate the selected procedure, not just the final stage-2 fit. This is why further reuse of the original folds calls for bounded experiments and explicit acknowledgement of selection exposure. [scikit-learn nested-CV example](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html)

### Inferences
1. **Freeze a named research candidate and score contract before comparing anything else.** Bind hashes for code, config, ordered feature columns, raw inputs, cached features, stage-1 OOFs and folds to its predictions. Preserve V1 and V4 packages separately. Give results immutable experiment names rather than repeatedly overwriting `motif_oof.csv` and `motif_train.parquet`. Initial task: read/hash saved artifacts, no fitting.
2. **Audit the full centre-to-score dependency graph.** Require outer-label exclusion everywhere, and independently test centre-block exclusion for every score entering neighbour and wallet aggregates. Decide explicitly whether wallet summaries include self; if they are labelled “other payments,” compute true leave-one-out mean/max/min, including tied extrema, singleton wallets and self-payments. Keep `ctx_self_pct` as an explicit self channel if useful. Initial task: provenance assertions and small score-bank fixtures, no fitting. Any corrected training pipeline must use the minimal consistent outer-inner/final-inference recipe described above and be reevaluated rather than patched into an old CSV.
3. **Recompute the comparison and CI for exactly the frozen candidate.** Use raw V1 comparator, the frozen blend function, AP/precision/recall at ceil(1% of each evaluated window), and the supplemental global top402/top1250 diagnostics. Separate changed normalization from added features in the report. Correct the old bootstrap's candidate/baseline labels. Initial task: calculations on existing OOFs; no training. Do not promote a medium-slice gain if total AP or top1% fails.
4. **Close the existing robustness gates; do not relax them because V4 improved locally.** Require the full candidate pipeline on the prelocked wallet and temporal protocols, confirmation seed and a sparse-history stress if that risk remains relevant. In context stacks, all stage-score banks must be regenerated inside each supervised holdout; importing ordinary all-label OOF banks into B/C would breach the heldout-label boundary. Full unlabelled graph context can remain permitted. These are fitting tasks for the working agent, not performed by this research subtask. If unavailable, label the candidate provisional rather than asserting it passed.
5. **Reproduce the selected artifact from its extracted ZIP before another release.** Import/help and format PASS are necessary but do not establish end-to-end reproducibility. Run the documented command against raw supplied inputs with pinned dependencies, then require byte-identical CSV or an explicitly predeclared numeric/order tolerance. Make evaluation paths portable, update the V1-only PDF and old `validation_summary.json` if the package claims V4 methodology, and include candidate-specific manifests. Do not upload or submit until the user's explicit approval and all existing gates are satisfied.

### Gaps
- These controls cannot make one reused labelled week into an untouched independent final dataset. The limited-wallet, shared offline graph and adaptive experiment history remain limitations even after implementation.
- No promise of reaching the leaderboard's top rank follows from these findings. The immediate benefit is distinguishing repeatable model improvement from source/version, normalization and validation artifacts without disturbing the agent already running feature experiments.
